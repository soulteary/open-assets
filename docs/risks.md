# 当前风险与改进顺序

本记录针对 2026-11-07 的应用代码、部署脚本和 Compose 配方。依据是源码检查、临时目录复现及现有部署的只读检查；没有进行渗透测试、压力测试、依赖漏洞库扫描或完整灾难恢复演练。下面的优先级用于安排改进，不是漏洞评分，也不表示已发生攻击。

节点配置更新之后，项目增加了 Info、健康检查和受限恢复，内部证书也改为 Certs Maker 生成的 3650 天证书。这些措施改善观察与恢复过程；回滚校验和坏任务隔离已另行修复并验收，剩余发布、权限和数据一致性问题仍按下文记录。

## 1. 回滚没有校验实际提供服务的图片副本

原优先级：P1。状态：已修复，2026-11-07 在隔离环境和既有部署验收。

此前命令校验完整快照，却切换到另一个未校验的图片副本。现在回滚先核对清单仓库与 SHA，再校验完整快照和实际图片目录的文件集合、类型、大小、SHA-256，拒绝符号链接、路径逃逸、缺失和额外文件；切换后再次核对图片，切换或校验失败时尝试恢复原 current 链接。正常发布也使用同一个图片激活函数。

不自动修补或覆盖损坏版本，避免把本地损坏掩盖成成功回滚；应从可信备份恢复版本后重新执行。仍依赖本地清单可信、文件系统正常以及管理员不并发修改目录。恢复链接本身遇到磁盘 I/O 错误时也可能失败；跨文件、进程崩溃与断电的一致性不由这些校验保证，见第 6、7 项。

## 2. 单个损坏任务会阻断整轮队列处理

原优先级：P2。状态：已修复，2026-11-07 在隔离环境和既有部署验收。

此前排序时在逐任务异常处理之外解析全部 JSON，坏文件会导致 Worker 反复退出。现在逐个限长读取普通文件，校验任务结构、时间字段、状态、仓库/SHA/类型派生的 ID 与文件名；只对有效待处理任务排序。坏记录移动到 state_root/quarantine/<随机标识>/record，旁边 reason.json 保存原文件名、时间和异常类型，不删除原始内容。

隔离或任务状态落盘失败会记录错误，不阻止本轮其他任务；整轮文件系统 I/O 失败按 4 至 60 秒退避重试。日志不输出任务正文或异常文本。正常发布失败仍标为 failed，需明确 retry，不自动重置；隔离任务不自动重放。隔离目录没有自动清理或外部告警，应纳入容量与备份管理。其他历史扫描、磁盘耗尽风险仍见第 3 项。

## 3. 容量限制不能约束整个部署

优先级：P1，用于持续收取内容的部署应先补齐运维控制。状态：本地保留、任务归档、Git/队列预算及流式发布已实现，并完成受限容器大文件实验；未对业务宿主机做整体资源耗尽实验。

Git fetch 已有时间、单进程虚拟地址空间、目录增长、单仓库及合计缓存预算；普通发布和恢复共用，详见[发布资源预算](resource-limits.md)。目录检查存在采样间隔，不能代替文件系统硬配额。Info 已展示各仓库本地占用和保留/清理摘要，并提供空间、inode 与发布预留提示；这些页面提示不发送外部通知。本地保留保护 current、回滚点、固定 SHA 和在途/失败任务，详见[历史清理](retention.md)。队列新增活动记录、含归档和隔离的合计记录及预留字节准入上限。普通发布与恢复均以文件流上传、分块读回校验，blob 导出也不再整文件读入内存。归档、清单、Git 历史和 S3 对象仍会累积；没有默认外部告警，Compose 也没有为主要应用设置完整资源限额。

持续 Push、大历史仓库、异常大对象或长期积累均可能耗尽磁盘、内存或处理时间，并影响同机 Gitea、存储和认证服务。只有签名正确且匹配配置的事件才能入队，但仓库写入者仍能消耗资源。

建议设置磁盘/内存告警、Gitea 仓库配额、容器资源限额和发布速率限制，按部署容量调整已有预算，按需启用本地保留策略，定期检查归档和未纳入自动清理的数据。大规模部署仍需任务索引，避免准入时扫描大量历史。

## 4. 默认 OC 账号权限较大，仓库之间也不构成租户隔离

优先级：P1，开放给更多使用者前应调整。状态：源码确认。

`scripts/initialize-services.py` 给初始 OC 账号绑定 `consoleAdmin`；它是管理账号，不能按普通上传账号使用。Stargate 的密码认证只增加入口检查，不会降低 OC 的 IAM 权限。默认账号和共享入口密码也不适合需要按人审计的团队。

Publisher 使用同一个 S3 身份访问全部已接入仓库前缀，并复用同一只读 Deploy Key。写入指定版本前先读取比对是应用约束，存储策略仍允许 PutObject；对象的“不可变”没有由对象锁或拒绝覆盖策略独立保证。Publisher 身份或进程失陷时，可以影响其授权范围内的其他仓库。Webhook 共享密钥泄漏也会影响所有白名单仓库的事件可信度，不过发布仍从固定远端检查提交。

建议按人创建 IAM 账号，区分日常读写和存储管理；缩小默认 OC 操作范围，建立密钥轮换与离职回收流程。若仓库属于不同信任方，应使用独立发布身份、密钥、队列乃至部署，而不是仅新增白名单。对需要保留保证的附件评估对象版本控制或存储侧不可变策略，并先验证与发布重试的兼容性。

## 5. 附件入口允许发布主动内容

优先级：P2；接收不可信内容时提高优先级。状态：源码确认，未做浏览器攻击验证。

图片扩展名有白名单，但 `public/` 的其他文件按 MIME 类型作为附件对象发布。HTML、SVG 等内容可以在公开 OSS 主机上以内联内容打开，当前没有统一的 Content-Disposition 下载策略或 CSP sandbox。`nosniff` 不是恶意内容扫描，也不能阻止合法 HTML MIME 类型执行脚本。

管理入口位于不同主机且使用主机级 Cookie，不能由此直接推断已存在管理会话窃取或认证绕过。但同一可注册域下的公开主动内容仍有站点信誉、钓鱼和同站请求方面的风险，需要在应用保留 Origin/CSRF 校验的前提下评估。

建议将不可信附件放到独立可注册域；按内容用途设置强制下载或经过验证的 CSP sandbox，限制可内联格式。改变下载头前测试图片引用、PDF、Range 和文件名兼容性。明确仓库作者的信任范围，并考虑恶意文件扫描。

## 6. 跨系统发布和配置接入都有中间状态

优先级：P2。状态：源码确认，部分失败重试已有测试覆盖。

Git、S3、本地图片链接与任务记录没有联合事务。版本对象逐个上传，任务未 published 时其中部分对象可能已公开；图片链接切换与状态持久化之间也存在进程中断窗口。自动任务第二次检查分支头之后仍可能收到新 Push，当前实现不能保证 current 始终等于瞬时 Git HEAD。

`repo ensure` 依次修改 Gitea、IAM 和本地配置。中途失败可能留下仓库、Key、Hook、权限或已更新的配置，不能把失败理解为没有任何改动。幂等重试有助于收敛，但不等于事务回滚。

已有恢复、核对与显式结案命令，仍需持续补充关键中断点恢复测试及按需的发布完成标记。需要“完整版本才可访问”的场景应在读取入口增加显式完成标记控制。接入失败先检查阶段、备份和运行状态，再执行同参数重试。

## 7. 备份、内部证书与单机可用性依赖运维

优先级：P1，业务依赖此服务前应完成恢复演练。状态：脚本与文档确认，未完成全量灾难恢复验证。

配方不默认安装定时异机备份和外部告警通知；现有部署是否另行配置需单独核查。内部 CA 与叶证书现为 3650 天，Info 展示到期与容量，但仍需私钥轮换和到期前替换。Gitea、OtterIO、任务与图片同机存放，单机或数据盘故障可能同时影响源数据、公开读取和本机备份。

`backup.sh` 不停止写入，也不包含 Traefik。`snapshot.sh` 停应用后打包，但 Traefik 仍可能更新 ACME，脚本退出时按固定列表启动服务，不恢复原先的启停状态。tar 与 SHA-256 校验不能代替应用恢复验证。

建议部署加密异机备份、证书与容量告警，并验证 Gitea 仓库/数据库、对象/IAM、SSH 主机密钥、私有 CA 和 ACME 的完整恢复。为快照安排一致性窗口，记录并恢复服务原状态。按业务要求确定可接受的数据丢失与恢复时间。

## 8. 固定拓扑和供应链验证仍有边界

优先级：P2。状态：源码确认。

域名节点名现在可配置，但路径、Compose 项目、网络、IP 和端口仍有固定值，不支持仅设置 NODE_NAME 就在同机部署第二套实例。共享 edge 网络上的容器具备后端网络可达性，网络可达不代表具有应用权限，但不应视为完全隔离。宿主机管理员、Docker 权限及可修改私有配置的人均在信任范围内。

应用镜像引用固定摘要，但 Dockerfile 的 apt 软件包来自构建时仓库，Python 依赖没有哈希锁定，GitHub Actions 引用版本标签。固定版本不意味着已完成漏洞扫描或构建可复现性验证。

建议先统一可配置的拓扑边界与部署前冲突检查，按实际连接缩小共享网络；继续固定 Actions 提交、增加依赖哈希、SBOM、漏洞扫描和升级回归。以上检查通过前，不宣称任意多实例支持、完整供应链保证或所有依赖均无漏洞。

## 建议执行顺序

1. 回滚校验和坏任务隔离已完成，继续观察隔离记录并纳入备份。
2. 为现有部署配置容量/证书告警、资源预算和异机恢复演练。
3. 收紧日常 OC 权限，明确仓库作者与管理员的信任边界。
4. 根据内容来源决定附件域名、内联与下载策略，再完善保留清理、中断恢复和供应链检查。

已有控制与报告渠道见 [安全说明](../SECURITY.md)，发布状态机见 [发布流程](architecture.md)，维护方法见 [运行维护](operations.md)。

对象容量采用低频 ListObjectsV2 缓存，逻辑大小不代表底层磁盘使用。分页期间并发写入会产生时间范围内的近似结果；大前缀受请求预算和 24 小时续采期限约束，可能长期无法完成，应检查采样时间与状态。采集复用 Publisher 的既有凭据，执行路径只列表，但该 IAM 身份仍能发布；Info HTTP 容器不接触凭据和续页 token。

已增加[对象保留](object-retention.md)，默认只预览，显式启用后可删除未受保护历史前缀。当前 OtterIO 实测不执行 DeleteObject If-Match，因此实际清理只适用于确认由本应用独占写入的前缀，不能阻止外部管理员并行改对象的竞态。永久删除会使旧链接失效；中断可能产生部分删除版本，收据支持保守恢复而不提供事务回滚。未完成分片、非当前 S3 版本、未知对象、归档、清单、收据和备份仍需独立管理。

对象保留看板已分开记录预览、执行和最新尝试，并标记规划过期、策略变化与失败/跳过原因。它不提供实时删除余量、外部告警或整版事务证明；强制终止和响应丢失仍可能导致部分删除计数不完整。摘要写入失败不能作为对象未删除的证据，需结合原始收据和备份排查。

已完成/归档的 manual 任务仍按原规则去重；恢复历史对象可使用独立 restore-objects CLI，不需删除任务身份或重放终态任务。恢复提供完整读回校验和可重复执行，但不提供跨对象事务，不恢复未记录的 S3 属性；本地 public/图片副本可显式使用 --with-local 重建，默认不切换。Git 周期容量检查的瞬时超量、恢复记录保留和绕过锁的外部写入仍需运维约束。

2026-11-08 补充：恢复核对、显式结案、审计查询/归档及低频缓存已实现，属于诊断、证据和容量控制，不消除上述跨系统事务/故障边界。统一操作入口、参数预校验和 Info 说明改进见[易用性检查](usability.md)；剩余资源、权限、规模与运维缺口按该记录继续安排。
