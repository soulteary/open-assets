# 显式结案恢复

`close-restore` 用于人工复核后结案未结案或状态不确定的恢复。命令会在同一 Worker 锁内重新读取对象、本地副本和 current/published，通过后写入独立结案记录。它不修改原恢复报告，不重建内容，不切换版本，不解除对象清理屏障。

```sh
cd /app/open-assets
sudo ./scripts/open-assets \
  close-restore "$ASSET_KEY" "$ASSET_COMMIT" \
  --reason '已复核数据和引用，保留现有服务版本'
```

仓库 key 和完整 SHA 必须指向已启用仓库中的已知版本。`--reason` 必填，去掉首尾空白后为 1–256 个字符，不允许控制字符；只保存在私有审计中，不出现在 Info API。原因用于记录本次判断，不应填入密码等凭据。命令本身就是显式结案操作，没有自动结案定时器，也不接受 `--rollback`、`--with-local` 等修改服务版本的参数。

## 结案条件

1. 原恢复报告存在、可校验，属于当前 endpoint/bucket 范围，且未结案（running）或有不确定标记。缺失、损坏、范围已变或普通已完成报告都不能结案。失败但没有不确定标记的报告也不属于本命令的结案范围。
2. 在本次锁内重新运行[完整核对](restore-check.md)，不使用旧 check-restore 的成功记录作为授权。对象、本地 public、图片副本、引用、清理屏障五项必须全部通过。
3. current 和 published 必须实际存在并指向同一份合法在用版本，published 内容必须与该版本清单一致。两者都不存在虽然可能是合法的未发布状态，但本命令仍拒绝结案。
4. 当前版本可以是目标 SHA，也可以是其他一致的在用版本。命令只记录核对当时是否在用目标，保留现有选择；不会把“目标当前在用”推断为过去切换成功。应在结案原因中记录保留当前版本的判断。
5. 写入结案结果之前，再比较原报告字节摘要、目标清单、current/published 和屏障。证据发生变化则拒绝，不能覆盖新恢复的状态。

核对的内容范围是目标 SHA；当 current 指向其他版本时，只检查其他当前版本的引用与 published/清单一致性，不下载其他版本全部对象。命令使用既有维护预算和网络读取上限，会占用带宽和 Worker 锁，适合人工按需操作。应用锁不能阻止外部管理员并发改写；执行期间不要绕过应用锁变更对象或引用。

本命令针对该 SHA 当前保存的原恢复报告。若正常恢复重试成功并生成了新的 complete 报告，新报告不需要此命令结案；已有审计快照仍保留先前失败事实，不应人为重造不确定标记来补做结案。

清理记录为 deleting/complete 时，即使对象已齐全也不能结案。先通过正常恢复流程完整验证并处理屏障；结案没有绕过检查或强制选项。副本缺失、内容冲突、超时或权限失败也不能结案，可先诊断或恢复，再决定后续动作。

## 原报告与审计记录

原报告保持原字节及状态，所以 Info 的“最近恢复结果”仍可能显示 failed、running 或不确定；“恢复结案记录”单独展示本次人工结案。结案是对当时观测状态的显式确认，不补写过去没有证据的阶段，也不把失败历史改成成功历史。

每次执行创建随机 ID 的独立私有目录：

```text
state_root/restore-closures/<key>/<audit-id>/
├── intent.json  # 开始时间、目标、私有原因、执行 UID
├── source.json  # 本次读取的原恢复报告字节快照（如可校验并读取）
├── check.json   # 同锁内重新核对结果（如已运行）
└── result.json  # closed / refused / failed
```

audit-id 不使用请求指定的路径。文件先刷盘，再以不覆盖已有目标的方式发布；目录为 0700，文件为 0600。应用不会覆盖旧尝试或证据；重复执行仍重新核对并增加一条审计记录。每次尝试独立结案，不把先前中断目录改写成成功。`execution_uid` 是容器内进程 UID，不是经过认证的个人身份；共享 SSH 运维账号的人员归属仍需外部审计。

拒绝结案和可捕获失败也保留尝试记录。锁忙、参数/配置校验失败或审计目录尚未创建时的错误可能没有审计条目。已有 intent 但没有 result 表示尚未结案，可能仍在执行，也可能是强制终止、掉电或最终审计写入失败；不能根据核对快照中的 verified 推断已经结案。命令失败或响应丢失不证明结果文件未落地，应检查私有审计并重新核对。

这些记录是应用层保留的证据，不是不可篡改存储或数字签名。具备宿主机写权限的管理员仍可改动文件。Info 展示成功结案时，会核对相应原报告/核对快照的摘要及绑定关系，发现损坏就显示不可确认；需要长期审计时，应备份到独立且有访问控制的存储。结案不会刷新内容的保留时间或新增固定保留引用，之后正常容量清理仍按既有策略执行。

## 结果与退出码

标准输出为 JSON，不输出私有原因或原始异常请求。退出码：

- 0：`status=closed`，本次结案结果已写入。
- 1：`status=refused` / `failed`，或未能完成命令；reason 为有限原因代码。审计 I/O 故障时可能只有通用错误和未完成 intent。
- 2：Worker 锁忙（JSON busy）或参数用法错误（argparse 输出）。

结案不与 S3、多个目录和文件系统组成联合事务。它的持久化效果是审计结果；对象和在用版本不变。后续正常发布、恢复或人工修改可以改变现场，同一 SHA 的新恢复也会更新原报告。旧结案只覆盖其 source.json 保存的那一次原报告，不覆盖新尝试。

## Info 展示与备份

[Info](info.md#恢复结果与状态核对)显示每仓库最近启动的结案尝试。成功结案、拒绝、失败、未完成和报告不可用分开表示；保留当前其他版本、原报告不确定以及后续证据变化均有提示。网页不提供结案按钮，不自动执行重新核对。

完整审计目录与原恢复报告、清单一起纳入 Publisher 状态备份。结案审计不参与自动历史版本清理；使用[审计查询与归档 CLI](restore-audit.md) 默认预览，显式 --apply 后才校验并移出在线目录，归档包仍需私有备份。Info 每仓库最多读取 512 个尝试目录，总扫描预算两秒，intent/result 各最多 8 KiB，证据快照各最多 16 KiB。超限、坏记录、链接或缺失证据会显示不可用，不回退到旧成功。归档前确认没有结案进程，保留目录结构和全部文件；不要只保留 result.json。
